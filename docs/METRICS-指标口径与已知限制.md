## 1 指标口径（含表述红线）

### 1.1 orchestrator-agent（编排器）

测试集：32 条 = 纯政策查询 7 + 纯业务 7 + 混合任务 7 + 边界模糊 9 + 三轮链路 1 + 上下文传递 1。
数字来源：`orchestrator-agent/eval/results.json`。

| 指标 | 数值 | 口径 | 定位 |
|---|---|---|---|
| **期望工具覆盖率** | **96.9%（31/32）** | 期望被调用的工具是否都真的被调用了；判定规则 `set(expected).issubset(set(actual))`，即**子集判定，多调不判错**。衡量**覆盖**而非"调得准不准" | ⭐ **主要业务指标** |
| 边界模糊场景 | 88.9%（8/9） | 模糊 / 口语化 / 情绪化 / 缺订单号输入下仍正确路由 | 鲁棒性参考 |
| 三轮链路验证 | ✅ 通过（S31） | 查政策 → 建工单 → 查物流 | 能力边界 |
| 上下文传递验证 | ✅ 通过（S32） | RAG 答案传入客服 Agent 继续决策 | 能力边界 |
| 降级验证 | ✅ 通过 | RAG 离线时返回"知识库暂不可用"，不阻断主流程 | 可用性 |
| `keyword_accuracy` | 53.1%（17/32） | 最终回答是否**逐字包含**用例预设关键词 | ⚠️ **严格关键词命中，非业务准确率** |

**唯一失败用例**：`S28`（工具未按预期调用）。

### ⚠️ 表述红线（README 与所有对外材料都必须遵守）

| ❌ 禁止表述 | 问题 | ✅ 正确表述 |
|---|---|---|
| "系统准确率 96.9%" | 96.9% 只测了**期望工具是否都被调用**，没测回答质量、没测端到端体验 | "期望工具覆盖率 96.9%（主要业务指标）" |
| "工具调用准确率 96.9%" | 判定是**子集口径**（多调不判错），叫"准确率"会让人误以为测了调用精度 | "期望工具覆盖率 96.9%（子集判定）" |
| "准确率 53.1%" | 会让听者以为系统答对一半 | "关键词命中率 53.1%，是严格逐字口径，仅作参考" |
| 只给 96.9% 不给 53.1% | 回避不利数字，被追问时更被动 | 主动给出两个数字 **并解释口径差异 + 附逐例归因** |
| 把两个数字做加权/平均 | 口径不同，不可合并 | 分开陈述，各自标注口径 |
| "96.9% 准确率，53.1% 是另一套算法" | 模糊其辞，像在掩饰 | "前者是期望工具覆盖率（子集判定），后者是回答逐字包含关键词的比例" |

**为什么 `keyword_accuracy` 只有 53.1%（必须在被问前主动解释）**：

该指标检查最终回答里是否出现用例预设的关键词。但**边界模糊场景的正确行为就是转人工**，
或建工单由业务侧补全信息，回答形如"已转人工，原因：…"，这类回答**天然不含政策原文关键词**——
也就是说，**安全的正确行为会被这个指标判为未命中**。

**15 条未命中逐例归因**（可复核，数据源 `eval/results.json`）：

| 类别 | 条数 | 用例 | 说明 |
|---|---|---|---|
| **正确转人工**（设计内安全行为） | **11** | S17 S18 S19 S20 S21 S24 S25 S27 S29 S30 S32 | 缺订单号 / 信息不足 → 按设计转人工 |
| 业务办成但回答未复述关键词 | 2 | S12（换货成功）S31（退款成功） | 工具正确、业务真实完成，仅回答措辞未复现关键词 |
| 风险规则正确拦截 | 1 | S11 | 物流停滞 ≥3 天 → 正确拦截转人工 |
| **测试数据缺陷**（与系统无关） | 1 | S15 | 用例用了库中不存在的订单号 `ORD-2001` |

**结论：15 条里 0 条是"回答了政策问题却答错"。**

**所以：53.1% 低是口径问题，不是系统答错一半。** 但也不能因此说它"不重要"——
它的价值在于暴露了"用关键词衡量生成质量"这个方法本身的局限，这是我后来把评估重点
放到**期望工具覆盖率**和**行动是否正确**上的原因。

## 2 已知限制

> 本文替代早期的 `docs/limitations.md`（那份写于 P0 之前，其中多条已在 P0/P1/P2 修复）。
> **已修复项在文末列明**，避免与旧文档矛盾。

### 2.1 安全与权限

| 限制 | 现状 | 影响 |
|---|---|---|
| 审批人无金额分级 | 任意 `agent` 可批准任意金额 | 生产环境应做"超过阈值需 `admin`"分级 |
| Demo 账号口令硬编码为 bcrypt 哈希 | 三个演示账号写在 `auth.py` | 生产必须迁到用户表 + 口令策略 |
| Cookie `secure=False` | 本地演示走 http | 生产必须 `True`（仅 HTTPS 传输） |
| 无限流 | 无 rate limit | 恶意调用可打爆 DeepSeek 余额 |

### 2.2 业务流程

| 限制 | 现状 | 影响 |
|---|---|---|
| 资金类是模拟执行 | `process_refund` / `refund_price_diff` / `urge_delivery` / `process_exchange` 只写状态 | 无真实支付链路（刻意的安全边界） |
| 退款金额依赖提取 | 用户未说金额时提取为 `0`（不编造） | 演示需显式说金额；生产应由业务系统带出金额 |
| 进入待审核无通知 | 无推送提醒客服 | 待审核工单可能被长期搁置 |
| 改动 `proposed_action` 后旧方案失效 | 当前实现是"批准即执行原动作" | 更严格应记 `version` 并在批准时比对 |
| 风险规则靠枚举 | 敏感词/组合模式/物流停滞，确定性代码 | 覆盖不了未写进去的表达方式 |

### 2.3 架构与运维

| 限制 | 现状 | 影响 |
|---|---|---|
| 单线程 uvicorn | 无并发处理 | 多用户同时请求会排队 |
| SQLite 单文件 | 三库各自本地文件 | 无法水平扩展；换 PostgreSQL 需改存储层（状态机与审计设计不用动） |
| 无会话记忆 | 每次请求独立 | 用户说"刚才那个订单"无法理解 |
| 无监控告警 | 进程崩了不会通知 | 无故障感知能力 |
| 无压测 | 未测吞吐/延迟上界 | 不知道容量边界 |
| 子 Agent 只有 2 个 | Supervisor 只挂两个工具 | 扩展到 10 个 Agent 需重新设计路由 |
| 历史工单无审计 | `ticket_audit` 表为本次改造新建 | 改造前的工单审计时间线为空 |

### 2.4 评估

| 限制 | 现状 | 影响 |
|---|---|---|
| 测试用例全部手写 | 无真实用户数据 | 对真实用户分布无感知 |
| 无对抗样本 | 未测 prompt 注入、脏话、超长文本 | 安全健壮性未验证 |
| 部分指标口径偏弱 | 如 `keyword_accuracy`、rag 的来源正确率 | 已在 1.1 说明，不掩盖 |
| 评估手动触发 | 改代码不自动跑回归 | 已知代价：本次就发现集成测试落后了两轮改动（见下） |

## 5 一次值得记的教训：测试落后了两轮改动

交付 P2 前检查时发现 `orchestrator-agent/tests/test_integration.py` 有 **11 个用例失败**，
而代码本身没问题。真因有三层：

1. **流式输出那轮**给 LLM 传了 `config=`（回调所需），但测试里的假 LLM `invoke()` 没接这个参数
2. **P1 认证那轮**让端点必须登录，但测试仍在裸调 → 全部撞 `401`
3. **最隐蔽的一层**：测试 patch 的是 `main.run_supervisor_with_trace`，而 `/gateway`
   早已改调 `run_supervisor_with_steps` —— **这个 mock 从来没生效过**

第 3 条意味着：那两个用例即使当时"通过"，测的也是空气。

**修复原则**：只补测试的**前置条件**（假 LLM 接受 `config`、先经真实 `/auth/login` 拿 Cookie、
修正 mock 目标与返回值结构），**不放宽任何断言**。修复后 14/14 通过（原 12 + 新增
"未登录 401""越权 403" 两条）。

**沉淀的规则**：**改了被测函数的签名或调用目标，必须同步跑一遍该仓的全量测试**，
不能只跑改动相关的那个测试文件。
