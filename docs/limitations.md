# 问题、局限与改进 — 三个项目的诚实评估

## 一、遇到的问题（按项目）

### rag-agent

1. **HF 被墙**：首次运行 ingest 时 huggingface.co 直连超时。改 hf-mirror.com 解决。
2. **ChromaDB 默认距离度量**：不指定 metadata 时默认 L2 欧氏距离，注释写"cosine 相似度"名不副实。显式设 `hnsw:space: cosine` 解决。
3. **文档漂移**：CLAUDE.md 列出 5 份文档但仓库实际文件名不匹配，README 声称支持 pdf 但 ingest 只加载 md。
4. **外部 API 无超时**：openai SDK 调用未设 timeout，LLM 挂起会拖死整个请求。

### customer-service-agent

1. **mock 数据是 JSON 不是数据库**：面试问"数据库在哪"答不出。本次改为 SQLite 解决。
2. **评估重试污染**：早期版本 LLM 调用无重试，网络错误被记入失败案例，售后类准确率 20% 全是假阴性。
3. **测试集标注错误**：标注了几条 ground truth 有争议的 case（退差价超限期望 auto → 应为 escalate）。
4. **数据-规则-标注不对齐**：mock 数据的时间戳随机生成，导致期望正常的运单被规则标为"异常停滞"。

### orchestrator-agent

1. **模型名折腾**：deepseek-v4-flash 不存在 → 全空。deepseek-v4-pro 是推理模型 → token 全烧在 reasoning_content → 全空。最终 deepseek-chat 才对。
2. **max_tokens 太小**：分类任务设 10 → 模型解释性输出被截断 → 空 → 兜底全判 knowledge。200 才稳。
3. **httpx 走系统代理**：Windows 上 httpx 默认 trust_env=True，调 localhost 被代理拒绝返回 503。设 trust_env=False 解决。
4. **架构方向错误**：v1 做了一个 HTTP 路由器但以为是编排器。classify → route → return，本质是 if/else。推翻重做。
5. **子 Agent 业务不搭**：RAG 查年假 + 客服查快递，两个场景无关。换成客服政策文档才统一。
6. **chroma_db 文件锁**：RAG 服务未完全退出时无法删除 chroma_db，重新入库失败。taskkill 全杀解决。
7. **WSL 到 Windows 网络不通**：WSL 内 127.0.0.1 无法访问 Windows 侧服务，必须用 cmd.exe curl。
8. **cmd.exe 中文编码乱码**：所有 Windows 侧日志、curl 输出中文显示为乱码。

## 二、局限性（三个项目共同的问题）

### 功能层面

| 问题 | 现状 | 后果 |
|------|------|------|
| 无用户认证 | 接口裸奔 | 任何人可调 /gateway、/query |
| 无输入校验 | 消息直接传给 LLM | prompt 注入、超长文本 OOM |
| 无并发处理 | 单线程 uvicorn | 多用户同时请求排队等 |
| 无会话管理 | 每次请求独立 | 用户说"刚才那个订单"→ 不知道是哪个 |
| 无多轮对话 | 一问一答 | Supervisor 每轮能做工具调用但不能跨请求记忆 |
| 数据量太少 | RAG 4 文档 8 chunk, 客服 30 订单 | 随便问个没覆盖的就答不出 |
| 全是假数据 | 所有数据手写的 | 和真实业务分布无关 |

### 架构层面

| 问题 | 现状 | 后果 |
|------|------|------|
| 单点故障 | 三个服务各自独立但无健康检查 | 任意一个崩了编排器就降级 |
| 无监控告警 | 进程崩了不知道 | 面试问"怎么发现故障"答不出 |
| 无限流 | 无 rate limit | 恶意调用会打爆 DeepSeek 余额 |
| 无部署方案 | 只在本机跑 | 面试问"怎么上线"答不出 |
| 子Agent 只 2 个 | Supervisor 只能调两个工具 | 面试问"扩展到 10 个 Agent 怎么办"答不出 |
| 最多两轮工具调用 | 测试集最长链路是"查政策→建工单"，未覆盖三轮以上场景（如查政策→建工单→查物流→催派送） | 面试问"Supervisor 最多能调几轮"时能说出边界比答不出强 |

### 评估层面

| 问题 | 现状 | 后果 |
|------|------|------|
| 测试用例全部手写 | 无真实用户数据 | 对实际用户分布无感知 |
| 无对抗样本 | 无恶意输入测试 | 没测过 prompt 注入、脏话、超长文本 |
| 评估只用准确率 | 无延迟、无成本指标 | 面试问"性能瓶颈在哪"答不出 |
| rag-agent 无留出集（已修复） | ✅ 20 条分层留出，16 train + 4 holdout | 留出集覆盖全部 4 份文档 |

## 三、如何改进（按优先级）

### P0 — 面试前至少能讲的

1. **加输入校验层**
   - 空消息 → 400
   - 超长消息（>500 字）→ 截断提示
   - 非中文/纯符号 → 友好拒绝

2. **加健康检查端点**
   - GET /health → 检查子 Agent 是否可达
   - 面试讲："如果子 Agent 挂了，编排器不会崩，会降级返回。通过 /health 可以接入监控告警。"

3. **写清楚已知限制文档**
   - README 加一段"已知限制"
   - 面试主动讲，别等问

### P1 — 让项目更像企业级

4. **增加测试数据量**
   - RAG 文档从 4 份扩到 8 份（加投诉处理、价格保护、会员权益、发票政策）
   - 客服订单从 30 条扩到 80 条，覆盖更多状态组合

5. **加 /health 端点和日志持久化**
   - 编排器已有 gateway.db，补上 CPU/内存/子Agent 延迟的定期采样

6. **多轮对话上下文**
   - Supervisor 增加 session_id，同一 session 的 message 历史保留

7. **成本追踪**
   - 每次 LLM 调用记录 token 消耗
   - /stats 增加 total_tokens_used 字段

### P2 — 真正的差距

8. ~~容器化部署~~ ✅ Docker Compose 一键启动（2026-08-08 完成）
9. **真实用户测试**：找 3-5 个人发消息，记录哪些场景答不出
10. **A/B 评估**：supervisor prompt 两个版本对比准确率
11. **持续评估**：每次改代码自动跑回归测试（当前评估是手动跑的）

## 四、认清现状

这三项目是 **0→1 的 MVP 验证**，不是生产系统。它们证明了：

✅ 你能把 RAG 管道从文档入库到评估跑通  
✅ 你能设计 8 个工具的 Agent 并让安全边界生效  
✅ 你能做多 Agent 编排（Supervisor 模式）并让多轮决策正确  
✅ 你有数据库意识（两个 SQLite）和问题意识（知道差了啥）

但它们不是企业级：

❌ 没有真实用户验证过  
❌ 没有压测过  
❌ 没有安全加固  
❌ 没有运维方案  

面试时不要说"这是企业级项目"——说"这是 MVP，我知道差距在哪"。面试官要的不是完美，是自知。
