# 流式输出实现记录（2026-09-16）

> 目标：让 p1 编排器的客服对话界面「逐字吐答案」，而不是等整段生成完再一次性显示。
> 结论：**已实现并验证通过**（后端 SSE + 前端流式渲染），eval 回归无退化。

## 一、最初的设想 vs 实测结果

原计划（路子 A）：给内部 LLM 调用打 tag，流式层丢弃带 tag 的事件。
**实测后整条推翻**——不是打 tag 的问题，是更底层的三件事：

| # | 原本以为 | 实测发现 |
|---|---|---|
| 1 | 需要自己打 tag 才能定位是哪次 LLM 调用 | `metadata` 里**自带** `langgraph_node` / `langgraph_step`，白送 |
| 2 | 决策轮的 `content` 是空的，可直接按内容判别 | 决策轮**会先吐一句英文解释**（"I'll help you with both..."），content 非空 |
| 3 | 加了 `streaming=True` 就能收到 token 事件 | 加了也**一个事件都收不到** —— 真正的根因是 `config` 没传 |

## 二、根因：同步节点丢掉了 callbacks

对照实验（同一张图，只换节点写法，`streaming=True`）：

| 变体 | 节点写法 | chat model 事件 |
|---|---|---|
| V0 | `def node(state)` + `llm.invoke(msgs)` | **0 个** |
| V1 | `async def node(state)` + `await llm.ainvoke(msgs)` | **0 个**（反直觉） |
| V2 | `def node(state, config)` + `llm.invoke(msgs, config=config)` | **271 个 token chunk** ✅ |

**原因**：LangGraph 的同步节点跑在线程池里，事件回调靠 `contextvar` 传播，跨线程不复制 → 节点内部的 LLM 调用成了"黑盒"。
**修法**：节点签名带 `config: RunnableConfig`，并把它透传给 `invoke`。只有这一个写法有效（async 节点也不行）。

## 三、判定「哪一轮该给用户看」

p1 的 `supervisor_node` **同一个函数既负责决策又负责汇总**，所以必须区分两轮：

```
决策轮: content=0     tool_call_chunk=33   首 6 个 chunk: TTTTTT
汇总轮: content=339   tool_call_chunk=0    首 6 个 chunk: CCCCCC
```

实测 3/3 次稳定复现。**判定依据 = `tool_call_chunks`，不是 `content`。**

- 只靠 content 判别会失败（决策轮的英文解释会漏给用户）
- 加一句 prompt 硬约束（「调用工具那一轮不要输出任何文字」）后，决策轮 content 归零，**首个 chunk 就能判型**
- 仍保留 `revoke` 兜底：万一正文先吐、之后才冒出 `tool_call_chunk`，撤回本轮已推送内容

## 四、改动清单

| 文件 | 改动 |
|---|---|
| `supervisor.py` | ① prompt 加输出格式硬约束 ② `ChatOpenAI(streaming=True)` ③ 节点签名加 `config` 并透传 ④ 抽出 `_step_item()` ⑤ 新增 `stream_supervisor()` 异步生成器 |
| `main.py` | ① 新增 `POST /chat/stream`（SSE）② 前端 `send()` 改为读流 + 逐字渲染 ③ 发送中按钮变「停止」（AbortController） |

**没动的**：`/gateway` 老接口保持不变（eval 和向后兼容都依赖它）；p2 / rag 本轮不改。

事件协议（`stream_supervisor` 产出，`main.py` 转成 SSE）：

```
{"type":"status","phase":"tool","detail":"query_rag"}   正在调用工具
{"type":"token","text":"您好"}                          正文增量
{"type":"revoke"}                                       撤回本轮已推送正文（兜底）
{"type":"done","answer":...,"tools_used":[...],"steps":[...],"elapsed_ms":...}
{"type":"error","message":"..."}
```

## 五、验证证据

| 层面 | 方法 | 结果 |
|---|---|---|
| 后端生成器 | 直接消费 `stream_supervisor` | 194 个 token 事件、正文与 `done.answer` 逐字一致、决策轮英文未泄漏 |
| HTTP 层 | `httpx` 流式请求真服务 | `200 text/event-stream`；status 2.5s → 首 token 6.24s → done 7.07s |
| 前端 | Chrome CDP 真跑页面 | 按钮「发送→停止→发送」、回复长度 7→16→111→348 字逐步增长、**0 JS 错误**、localStorage 历史正确 |
| 观测台 | CDP 打开 `/ops` | 新记录正常入会话列表，工具分布 `query_rag ×2 create_ticket ×2`，0 JS 错误 |
| **回归** | `eval/run_eval.py`（32 用例） | 工具 **31/32 = 96.9%**、关键词 **17/32 = 53.1%**，**与 9-10 基线完全一致** |

## 六、踩到的坑（下次直接抄）

1. **`langgraph_node` 会被子 chain 继承**：它在节点内部的 `ChatOpenAI` RunnableBinding 上也带同一份 metadata。只按它收集步骤会多记一笔（实测 steps 多出 2 条）。→ 收集节点耗时/步骤要按 **chain 的 `name`** 过滤，只有 `langgraph_node` 用于过滤 chat model 事件。
2. **首 token 延迟 6 秒是 p1 的固有特性**，不是流式没生效：工具调用阶段（决策 2.5s + 工具 3.7s）本就没有正文可流。体验靠 `status` 事件（"正在调用 query_rag …"）兜。
3. **Chrome CDP 连 WebSocket 报 403**：需要 `--remote-allow-origins=*` 启动，或在客户端 `websocket.create_connection(..., suppress_origin=True)`。
4. **`taskkill //F` 在 git-bash 里不可用**（MSYS 不做路径转换）→ 直接写 `/F`。
